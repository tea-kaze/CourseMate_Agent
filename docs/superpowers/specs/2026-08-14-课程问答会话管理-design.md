# 课程问答会话管理（问题 5）设计文档

日期：2026-08-14

## 1. 背景与目标

**现状**：课程问答页面的聊天记录只保存在 Streamlit 的 `st.session_state`（单一会话）中，程序重启后全部丢失；没有新建、切换、保存会话的能力。

**目标**：

1. 会话持久化：会话与消息存入 SQLite，重启后仍可查看和继续。
2. 会话管理：支持新建、切换、删除会话，界面形式参考主流 AI 对话 Web 页面（侧边栏会话列表）。
3. 上下文压缩：长对话下，发送给模型的历史需要压缩，控制 token 成本并保持对话连贯。

## 2. 范围

**本次包含**：

- 会话的创建、列表、切换、删除。
- 消息持久化（用户问题与助手回答落库）。
- 会话标题自动生成（取第一条用户消息前 20 字）。
- 上下文压缩（增量摘要 + 最近消息窗口，详见第 7 节）。
- 页面侧边栏会话列表。

**本次不包含（YAGNI，后续可扩展）**：

- 会话重命名。
- 多用户/登录、权限隔离。
- 会话导出、搜索、置顶。
- 消息编辑、删除单条消息。

## 3. 架构总览

沿用现有分层：

```text
Streamlit 页面（2_💬_课程问答.py）
        │  HTTP（api_client）
        ▼
FastAPI（coursemate/app/main.py）
        │
        ├── chat_repo（会话/消息读写）
        ├── context（上下文压缩）
        └── agent service（LLM 问答，现有逻辑不变）
        ▼
SQLite（chat_sessions / chat_messages）
```

页面只负责展示与交互，会话数据一律通过 API 读写，不再依赖 `st.session_state` 保存聊天记录。

## 4. 数据模型

新增两张表（`coursemate/db/models.py`）：

### chat_sessions

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Integer PK | 会话 ID |
| course_id | FK courses.id，可空，索引 | 会话绑定的课程范围；空表示全部课程 |
| title | String(200) | 会话标题；首条消息后自动生成 |
| summary | Text，默认空 | 上下文压缩产生的对话摘要（第 7 节） |
| created_at | DateTime | 创建时间 |
| updated_at | DateTime，索引 | 最后活动时间，会话列表按此倒序 |

### chat_messages

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Integer PK | 消息 ID |
| session_id | FK chat_sessions.id（ondelete CASCADE），索引 | 所属会话，删除会话时级联删除消息 |
| role | String(20) | user / assistant |
| content | Text | 消息内容 |
| created_at | DateTime | 时间，同一会话内按此升序 |

## 5. API 设计

### 会话管理

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/chat/sessions` | 会话列表，按 updated_at 倒序；返回 id、title、course_id、message_count、时间 |
| POST | `/chat/sessions` | 新建会话，请求体 `{course_id?}` |
| DELETE | `/chat/sessions/{id}` | 删除会话（级联删除消息） |
| GET | `/chat/sessions/{id}/messages` | 读取会话消息，按时间升序 |

### 问答（扩展现有 `/chat`）

请求体在现有 `message / course_id / history` 基础上增加可选字段 `session_id`：

- `session_id` 为空时自动新建会话（兼容现有页面与调用方）。
- `session_id` 存在但找不到时返回 404。
- 传入 `session_id` 时，请求体中的 `history` 参数不再使用，历史一律从数据库按时间读取（避免前后端各持一份、状态不一致）。
- 问答成功后：写入用户消息与助手消息；首条用户消息生成标题；刷新 `updated_at`；执行上下文压缩（第 7 节）。
- 响应增加 `session_id` 与会话标题，页面据此切换/刷新。

## 6. 页面设计（Streamlit）

### 侧边栏

- 课程范围选择（沿用现在的下拉框，绑定到当前会话的 course_id）。
- 「＋ 新建会话」按钮：创建空会话并切换过去。
- 会话列表：单选高亮当前会话，点击即切换；对当前会话提供「删除」按钮（删除后自动切到最近的会话）。
- 列表项展示标题与最后活动时间（简洁展示，如 `标题 · 日期`）。

### 主区

- 顶部显示当前会话标题。
- 消息区用 `st.chat_message` 渲染当前会话全部消息（每次交互从 API 重新读取，保证数据一致）。
- 底部 `st.chat_input` 输入问题；发送后调用 `/chat`，成功后刷新消息。
- 无会话时显示空状态引导（「点击侧边栏新建会话」）。

### 状态管理

- `st.session_state` 只保存 UI 状态：`qa_session_id`（当前会话）、`qa_pending_question`（发送失败时保留输入）。
- 消息内容一律从 API 读取，重启后自动恢复。

## 7. 上下文压缩设计（重点）

### 7.1 问题与目标

会话无限增长后，把全部历史发给 Agent 会超出上下文窗口并推高 token 成本。当前 `/chat` 只取最近 10 条，简单但会丢失早期关键信息（用户偏好、结论、未完成事项），长对话会答非所问。

压缩的目标：

1. 控制每次请求发送给模型的 token 量。
2. 长对话仍保留关键信息（关键问题与结论、用户明确要求、未完成事项）。
3. **压缩只作用于发送给模型的上下文，不影响用户可见的完整消息**（UI 始终展示全部消息）。
4. 压缩失败不阻塞问答。

### 7.2 方案对比

#### 方案 A：滑动窗口（只发最近 N 条）

- 优点：零额外成本、实现最简单。
- 缺点：早期上下文彻底丢失，连续追问同一主题时会失忆。
- 适用：以短会话为主的场景。

#### 方案 B：摘要压缩（LLM 生成对话摘要，随请求携带，摘要持久化）

- 把超窗的旧消息交给 LLM 压成一段「对话摘要」，与最近 N 条消息一起发给 Agent。
- 摘要保存在 `chat_sessions.summary`，后续超窗时做**增量更新**（旧摘要 + 新增旧消息 → 新摘要），避免每次重复总结全部历史。
- 优点：长对话保持连贯，token 可控，摘要只生成一次/增量更新，长期成本低；这是主流 AI 对话产品的常见做法。
- 缺点：超阈值时多一次 LLM 调用；摘要本身有少量信息损失；摘要 prompt 需要设计好。

#### 方案 C：混合（滑动窗口 + 摘要 + 检索注入）

- 在 B 的基础上额外把课程资料检索结果注入上下文。
- 本场景中课程检索已由 Agent 的 `search_knowledge` 工具完成，无需重复注入，故不采用。

**推荐：方案 B（增量摘要 + 最近消息窗口）。**

### 7.3 触发条件与预算

每次 `/chat` 请求时按顺序判断：

1. 会话消息数 ≤ `CHAT_SUMMARY_THRESHOLD_MESSAGES`（默认 20）且估算长度 ≤ `CHAT_HISTORY_CHAR_BUDGET`（默认 6000 字符）→ 不压缩，全部发送。
2. 超过阈值 → 进入压缩流程。

token 估算不做精确分词：`估算 token ≈ 字符数 / 2`（中英文混合场景的保守近似，避免引入额外 tokenizer 依赖）。

### 7.4 压缩算法

设会话消息按时间升序为 `M1..Mn`：

1. 保留最近 `CHAT_KEEP_RECENT_MESSAGES`（默认 10）条作为「近窗消息」。
2. 更早的消息 `M1..M(n-10)` 为「待压缩段」：
   - `summary` 为空：对 `M1..M(n-10)` 生成摘要。
   - `summary` 非空：把 `旧 summary + M1..M(n-10)` 一起压缩生成新摘要（增量更新）。
3. 发送给 Agent 的消息序列为：

   ```text
   [system 提示词（现有）]
   [user: 会话摘要]（若有摘要）
   [近窗消息逐条]
   [本次用户问题]
   ```

4. 问答成功后，把新 `summary` 写回 `chat_sessions.summary` 并刷新 `updated_at`。

### 7.5 摘要 prompt

```text
请将以下对话压缩为简洁的对话摘要（中文）。
必须保留：关键问题与结论、用户明确表达过的偏好或要求、尚未完成或待继续的事项。
省略：寒暄、重复内容、与主题无关的细节。
只输出摘要本身，不要解释。
```

### 7.6 失败降级

- 摘要生成失败（网络/API 错误）：跳过摘要，降级为方案 A（只发送最近 10 条），记录日志，**不阻塞用户提问**。
- 摘要写入失败：保留旧值，不影响本次回答。

### 7.7 配置项（config.py 新增）

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| CHAT_SUMMARY_THRESHOLD_MESSAGES | 20 | 超过该消息数触发压缩 |
| CHAT_HISTORY_CHAR_BUDGET | 6000 | 消息估算字符预算（约 3000 token） |
| CHAT_KEEP_RECENT_MESSAGES | 10 | 压缩后保留的最近消息条数 |

### 7.8 代码组织

- 新增 `coursemate/agent/context.py`：`build_chat_context(messages, summary, llm)` 与 `summarize_messages(...)`，纯函数、可单测。
- `coursemate/app/main.py` 的 `/chat` 路由负责：读消息 → 调 `build_chat_context` → 调 Agent → 保存消息/摘要。

## 8. 错误处理

- `/chat` 调用 Agent 失败：不写入任何消息，返回错误；页面提示失败，输入内容保留在 `qa_pending_question` 便于重试。
- 会话不存在：API 返回 404，页面自动切回会话列表。
- 删除会话：级联删除消息；页面删除后自动选中最近会话。
- 压缩摘要失败：按 7.6 降级，不影响主流程。
